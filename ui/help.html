Reference / User guide

Everything llmproxy does, and why

Each feature below answers the same six questions in the same order: what it is, why it was built, how to switch it on, how to drive it, where to watch it work, and what it costs you. Press / to filter.

Nothing in the guide matches that filter.

Getting started

llmproxy is a local-first proxy that sits between your agent CLIs — Codex, Claude Code, Copilot CLI — and every model provider you use. Because it is the only component that sees all of them, it can do things none of them can do for themselves: route each request to the model that suits it, absorb an outage, remember what an earlier session learned, and price the whole thing.

01

Starting and stopping

basics
What it is

One background daemon per listen address. Starting again reuses the running one rather than launching a second, so every agent session shares a single router, a single decision audit, and a single spend ledger.

Use it
cargo build --release
cp llmproxy.example.toml config.toml   # then edit it
./target/release/llmproxy              # start or reuse
llmproxy --restart                     # replace the running daemon
llmproxy --shutdown                    # stop it

Startup prints the proxy address, the admin address, and the log file path.

Config

Discovery order is --config, then LLMPROXY_CONFIG, then ./config.toml, then ~/.llmproxy/config.toml. Your local config.toml is git-ignored because it holds credentials; llmproxy.example.toml is the documented, credential-free reference.

Caveat

Editing the config file does not make the change live on its own. Either restart, or make the edit through this admin interface, which validates and swaps the running state atomically.

02

Turning on this interface

basics
What it is

A loopback-only web interface for watching and editing the running proxy. Nothing else in this guide is visible without it.

Turn it on
[admin]
enable = true
# listen_address = "127.0.0.1:11180"   # omit for a random port

Then llmproxy --restart. The URL is printed at startup and repeated in the footer of the admin pages.

Caveat

The admin interface is unauthenticated by design and must stay bound to loopback. Do not expose it on a routable address or put it behind a tunnel.

03

The three modes, and launching an agent

basics
What it is

Every launcher runs in one of three modes. The mode decides how much say the proxy has over where a request goes.

modewhat happensuse it when
--proxypure protocol adapter: every generation goes to the default provider, no routing prompt, no extra toolsyou want the adapter and nothing else
--intercepta local model is asked first; it either answers, or emits PASS and the untouched original goes externalyou want cheap local answers for the easy turns
--integratedthe agent's model becomes Auto and a local triage model picks one of your [integrated.targets.*]the default, and what the rest of this guide assumes
Use it
llmproxy --codex                    # integrated is the default mode
llmproxy --claude
llmproxy --copilot

llmproxy --proxy --claude           # explicit overrides
llmproxy --intercept --codex
llmproxy --integrated --copilot

llmproxy --claude -- --model sonnet # arguments after -- go to the agent
See it

Overview › Start an agent builds the exact command for the agent and mode you pick, ready to copy.

Caveat

An explicit model bypasses integrated triage. Only Auto — which the integrated launchers set for you — reaches the router. A named alias or a provider/model pair always wins outright.

Core concepts

Five nouns carry the whole system. Everything after this section is built out of them.

04

Providers, targets, triage, aliases, projects

vocabulary
Provider

An upstream connection: a kind that selects the wire protocol (openai-compatible, openai, anthropic, copilot), a base URL, and a credential. Credentials are either proxy-owned (api_key_env) or a borrowed CLI login (auth = "codex-oauth" / "claude-oauth"), which bills against your plan instead of per token.

Providers edits these one at a time; saving rebuilds only that connection.

Target

A named destination the router can choose: a provider, a model, and a hint in plain English describing the work it owns. The hint is what the triage model actually reads, so it is the highest-leverage string in your config. Optional extras: reasoning_effort, strength (higher is stronger; only the ordering matters), failover, second_opinion, and default.

Exactly one target may set default = true. That is the catch-all — ROUTE_DEFAULT resolves to it instead of falling through to first-upstream-model discovery.

Routing › Triage setup › Integrated targets

Triage

A separate request to a small local model, carrying a copy of the conversation and one zero-argument tool per target. Whichever tool it calls is the route. The copy never mutates the request that goes upstream, and caller credentials never reach the local provider.

Routing › Policy & test is where you edit the routing policy and test a single prompt against it.

Alias

A stable client-facing model name pinned to one provider and model, so a tool that hardcodes gpt-5.4 can be pointed anywhere. Any configured provider can also be addressed directly as provider/model without declaring an alias first.

Models

Project

The repository a session is working in, identified by the nearest .llmproxy.toml at or above the working directory. It scopes routing overlays, spend attribution, and shared memory. See Project overlay.

Routing

Six features shape where a request ends up. They compose: a verb beats a sticky pin, a sticky pin beats the cache, the cache beats triage, and health beats all of them by removing a provider from consideration entirely.

05

In-band routing verbs

routing on by default
What it is

A small closed set of words recognised at the very start of your newest message, which override routing for that turn and are stripped before anything is forwarded.

Why

Agent CLIs give you no way to set a per-message header. The message text is the only channel back into the router, so it had to become one — but only narrowly. The set is closed, matched exactly, and only at the start of the newest message, because a loose match would silently eat a sentence you meant to send.

Turn it on
[integrated]
verbs = true

Routing › Triage setup › Recognise routing verbs

Use it
  • triage: re-run routing for this message, ignoring the pin
  • unstick: drop the conversation's pin entirely
  • local: answer here, with the routing tools withheld
  • default: take the catch-all target
  • backend: — any target name — pin that route directly, with no triage latency at all
  • remember: recall: forget: manage project memory
  • \local: a leading backslash sends the word literally
See it

Activity › Decisions — the card's reason names the verb that decided the route.

Caveat

Recognised prefixes are stripped from every user turn, not only the newest, so the triage model can never read a stale directive as if it were current. While verbs are on, a target may not be named after one.

06

Sticky routing and its bounds

routing
What it is

One conversation stays on one provider, so a multi-turn task does not wander between models mid-thought. Four independent bounds decide when that choice is reconsidered.

Why

The TTL alone was a sliding window: agent CLIs send a session header on every turn, and each successful redirect re-inserted the entry, so the first message of a session chose the route and kept it for as long as you kept working. No value of sticky_ttl_secs changed that, because it only ever governed idle gaps. The other three bounds exist because they each bound something the TTL does not.

Turn it on
[integrated]
sticky_ttl_secs = 1800           # idle gap only — slides on every turn
sticky_absolute_ttl_secs = 3600  # from the decision, never refreshed
sticky_max_turns = 0             # N turns then reconsider; 0 disables
sticky_policy = "escalate"       # or "pin"
sticky_capacity = 1024

Routing › Triage setup › Sticky routing

Use it
  • Absolute TTL — measured from when the route was chosen and never refreshed, so a long session is periodically re-triaged even under continuous use. This is the setting that actually bounds active work.
  • Turn bound — a pin serves at most N turns.
  • Drift — with embeddings on, a request far enough from the one that pinned the route reconsiders it. Set [integrated.embedding] retriage_below.
  • Escalate, never demote — under sticky_policy = "escalate" a re-triage may move the session up the strength ordering but never back down, so cost control survives without pinning quality to whatever the first message happened to be.
See it

Activity › Decisions distinguishes a sticky reuse from a fresh decision and names the bound that expired. When the escalate policy blocks a demotion the reason says so explicitly.

07

Embedding-cached routing and retry escalation

routing needs an embeddings provider
What it is

One local embedding per request buys three things at once: a cache that replays a near-identical past decision without calling the triage model at all, the drift check that reconsiders a pinned route, and retry detection that treats a re-ask as dissatisfaction and moves the request up one rank.

Why

Every routing decision is already audited with its prompt, so embedding the request and matching it against that audit turns the audit into a cache for free: triage cost drops, and identical requests route identically by construction rather than by luck.

Retry escalation exploits a signal only the proxy can see. Re-asking the same question a different way is dissatisfaction, and it is visible here: same conversation, near-identical embedding, no intervening tool use. That last condition is what keeps it honest — a similar follow-up after the agent has run tools is ordinary iteration, and escalating that would just cost money.

Turn it on
[providers.embeddings]
kind = "openai-compatible"
base_url = "http://127.0.0.1:18000/v1"

[integrated.embedding]
enabled = true
provider = "embeddings"
model = "Qwen/Qwen3-Embedding-0.6B"
threshold = 0.94        # replay a past decision at or above this
retriage_below = 0.0    # drift check; 0 disables
retry_escalation = true
retry_threshold = 0.93
capacity = 2048
ttl_secs = 86400
timeout_ms = 2000

Routing › Triage setup › Embedding-cached routing

Use it

Nothing to drive — all three are automatic. Retry escalation is the one you will feel: ask again in different words and the next answer comes from a stronger route, silently, with no setting to reason about at the call site.

See it

Live cache statistics sit directly under that block. Escalations appear in Activity › Decisions as "the request repeated a recent one with no intervening tool use, so it was escalated". The same signal feeds the leaderboard.

Caveat

Only replayable outcomes are cached: a rejection or a malformed control is always re-derived, and a cached decision naming a target you have since deleted is pruned rather than replayed. Every embedding failure is soft — routing never depends on the cache being reachable.

All three are disabled while reject sensitive is on, because a cached decision would skip screening that must fail closed.

08

Speculative triage

routing
What it is

The triage call and the presumed catch-all route are issued at the same time and the loser is cancelled, taking the triage round trip off the critical path.

Why

Most requests go to the catch-all. Waiting for triage to confirm what it was probably going to say is latency you can trade for tokens — and it is a trade you can measure, because the decision audit records how often triage disagreed.

Turn it on
[integrated]
speculative = true   # requires exactly one target with default = true

Routing › Triage setup › Speculate the default route

See it

Activity › Decisions — the reason ends with "the route was speculated on concurrently with triage". Compare the triage latency in the card footers before and after.

Caveat

Buffered speculation never reaches the conversation: if triage disagrees the task is aborted and its output dropped. It never runs with sensitive screening on — that would put the prompt in front of a provider before it had been screened — and never when a verb has already decided the route.

09

Project-scoped routing overlay

routing
What it is

A .llmproxy.toml in a repository, defining routes that apply only while you are working in it. One daemon still serves every project.

Why

Different repositories want different routing, and the natural place to record that is beside the code. The hard constraint is that a project file lives in a repository, and cloning an untrusted repository must not be able to decide where your prompts are sent or which key pays for them. So a project file may define only routes and aliases, and every provider it names must already exist in your user config — anything else is rejected by name.

Use it
# <repo>/.llmproxy.toml
[integrated.targets.docs]
provider = "anthropic"          # must already exist in your user config
model = "claude-sonnet-4-5"
hint = "documentation and prose work in this repository"

[model_aliases]
project-fast = { provider = "openai", model = "gpt-5.4-mini" }

A launcher finds the nearest one at or above the working directory. --project <dir> overrides it; --no-project disables it for that launch.

See it

The project name keys the selectors in Activity › Spend and Routing › Project memory. Merged project targets appear in the targets table like any other.

Caveat

Project targets merge with your user-level ones and win on a name collision; nothing user-level is removed. Validation rejects a second default = true after the merge. The scope travels to the daemon as a path inside the session token, and because that token is unsigned the daemon re-reads the file and re-validates it rather than trusting anything the token claimed.

Still open: two routes whose hints overlap have no tie-break. Keep hint wording disjoint.

10

Failover, quota, and circuit breaking

routing on by default
What it is

A target may name an ordered chain of other targets to try when it is unavailable. Separately, per-provider health tracking routes around a provider that is rate-limited or circuit-open.

Why

Rate-limit exhaustion mid-task is the sharpest failure in agent-assisted work, and the proxy owns every provider credential, so it is the one component that can absorb it: exhausted on A, continue on B, reported here rather than to the caller. Quota and outage are tracked separately because they need different recoveries — a 429 carries a duration the provider tells us about, while an outage gets exponential backoff behind a single half-open probe.

Turn it on
[integrated.targets.routine]
failover = ["backend"]        # per target

[integrated]
failover = ["PROVIDER_DEFAULT"]   # default chain for targets without one

[health]
enabled = true
failure_threshold = 4
open_secs = 30
max_open_secs = 600
max_rate_limit_secs = 900

Routing › Triage setup has a failover column on every target row; Settings › Provider health and circuit breaking holds the thresholds.

See it

That same Settings disclosure carries a live health table — provider, status, ok, failed, retry-in, last error — with a Clear health state button. Failover events append "Failover …" to the reason in Activity › Decisions.

Caveat

Failover fires only on a non-success status, which means the provider rejected the request before generating anything — so no work is billed or produced twice. An unhealthy provider is also withheld from the triage tool list so the model picks a working route in the first place, unless withholding would leave nothing: an empty route list is worse than an optimistic one.

Evidence and cost

Four features that turn "which model should I use" from an opinion into something you can look up. All of them are built on traffic that already happened in your repository, not on a public benchmark.

11

Spend meter and cost insight

evidence
What it is

Live per-project spend priced from your own rate table, plus the insight built on it: a proposed routing change, with the exact payload the routing editor takes.

Why

Four things would each have made the number untrustworthy, so each is handled explicitly rather than approximated:

  • Rates change, so config is the only source of truth and nothing is hardcoded. An exact model id wins, then the longest configured prefix, then *.
  • Cached tokens read at a steep discount and write at a premium, so a naive input-token multiplication overstated agent traffic badly. Cache counts now reach the ledger through every protocol adapter, normalised onto one convention.
  • Estimated counts are labelled as approximations rather than presented as precise figures.
  • Counters survive a restart in a month-bucketed ledger under ~/.llmproxy. It stores counters, never prices, so correcting a rate re-prices history instead of leaving a stale number behind.

And cost alone is never a reason to move a route. Pairing the spend figure with observed satisfaction is what stops the insight from recommending its way into a worse outcome.

Turn it on
[providers.openai.pricing]
currency = "USD"
# subscription = true   # bills against a plan: volume only, never a dollar figure

[providers.openai.pricing.models."gpt-5.4"]
input = 1.25          # per million tokens, as vendors publish them
output = 10.0
cache_read = 0.125    # defaults to the input rate when unset
cache_write = 1.5625
See it

Activity › Spend — month and project selectors, totals for input, cache, and output, breakdowns by project and by model, and Reset ledger. A summary tile also sits on Overview.

Cost insight is on the same page. When a cheaper route has enough evidence behind it and is not observably worse, you get a card reading target: from → to with cost per answer, sample sizes, satisfaction on both sides and the observed saving — and an Apply routing change button that writes it straight into the target.

Caveat

A provider with subscription = true reports token volume and no dollar figure, because a figure there would be a fiction. A provider with no pricing table reads as "unpriced" everywhere — never as zero.

12

Personal model leaderboard

evidence
What it is

A per-project ranking of the models this proxy actually routed to, scored on the aftermath it can observe: an immediate re-ask with no intervening tool use, an error, a broken stream.

Why

Public benchmarks rank models on generic tasks. What you want to know is which model does well on your work in this repository — and the proxy is already watching the aftermath of every answer, which is free implicit labelling. That yields a per-project ranking rather than an average one.

Turn it on

Nothing beyond a writable ~/.llmproxy. It scores best with retry_escalation on, since a re-ask is the strongest label available.

See it

Activity › Spend, below Cost insight: rank, provider, model, answers, retried, failed, satisfaction, cost per answer.

Underneath it, hint candidates proposes the terms that distinguish one target's observed prompts from the rest — useful raw material for rewriting a hint.

Caveat

Rows below the sample-size floor are shown but never ranked: a rank derived from a handful of requests is noise wearing a number's clothes. The panel names the current floor rather than leaving you to guess it. Cost breaks ties rather than driving the order, because a cheap route that gets re-asked is not cheap. Hint candidates are a frequency contrast, not a topic model, and are offered for you to edit rather than applied automatically.

Still open: the signal set is small. Whether you reverted an edit is the strongest label there is, and the proxy cannot see it without watching the repository.

13

Shadow requests

evidence
What it is

A sampled share of requests is also sent to a second target. One answer is returned to you; both are recorded and diffed here.

Why

It turns "is the expensive provider actually better" into something you can read side by side on your own prompts, at a cost you choose.

Turn it on
[integrated.shadow]
enabled = true
target = "PROVIDER_DEFAULT"
sample_one_in = 20
timeout_ms = 120000

Routing › Triage setup › Shadow requests

See it

Activity › Shadow — paired cards with the prompt, both answers, and a word-overlap percentage. The second answer is labelled "never seen by the caller". This feed polls only while its tab is open, because each entry carries two whole answers.

Caveat

Sampled requests are buffered rather than streamed, because a diff needs both complete answers. That is the reason to keep the rate low. Sampling is an exact one-in-N counter rather than a random draw, so the observed rate is exact and a replay is reproducible.

14

Second opinion on consequential requests

evidence config file only
What it is

Opt in per target: two providers answer the same request and both are shown, or a third reconciles them while being told to name the disagreements rather than smooth them over.

Why

Agreement is signal; divergence is the stronger one, and nothing else surfaces it. Reconciliation is told explicitly not to smooth, because a smoothed answer destroys the only thing a second opinion produces.

Turn it on
[integrated.targets.design.second_opinion]
target = "frontend"
mode = "present"          # or "reconcile"
reconciler = "backend"    # required for mode = "reconcile"

There is no editor for this in the interface. Use Settings › Configuration file or edit config.toml. The target-row editor preserves an existing second_opinion when you save other fields, but will not create one.

See it

In the agent's own answer — this is the one feature that surfaces to the caller rather than to this interface. present returns both answers under headings with an agreement note; reconcile returns one answer that names where the two disagreed.

Caveat

A tool call on either side cancels the comparison and the request is sent normally, because a composed answer is text and would silently drop the call. The agreement score is a word overlap, not a semantic judgement, and is labelled as such — treat divergence as a prompt to look, not as a verdict.

It costs two answers and gives up streaming for the requests it touches. That is the right trade for a design decision and the wrong one for everything else, which is why it is per-target rather than global.

Safety

Two answers to the same question — what should happen when a prompt contains a secret. One refuses; the other substitutes and continues. Pick deliberately, because the strict one switches several other features off.

15

Reject sensitive prompts

safety strict
What it is

A mandatory screening step before any local answer or external route. A prompt that fails screening gets a native, successful no-action response instead of being sent anywhere.

Why

It fails closed: if screening cannot complete, nothing goes out. The refusal reason names a safe category and never repeats the detected value.

Turn it on
[interceptor]
reject_sensitive = true

Routing › Triage setup › Local interceptor

See it

Activity › Decisions — decision reject, with the prompt shown as "prompt redacted" and no Test this prompt button. Screened bodies are omitted from the trace log too.

Caveat

This is the switch with the widest blast radius. It disables sticky routing, the embedding cache, drift re-triage, retry escalation, speculative triage, and memory writes — each because they would otherwise skip or outlive screening that must fail closed: every request is screened and routed on its own merits. See What disables what. Pure --proxy launcher sessions disable it to stay prompt-free.

16

Redact and route

safety permissive
What it is

Detected secrets become stable placeholders, the request routes normally, and the originals are put back as the response streams.

Why

reject_sensitive is binary, which turns "there is a credential in this file" into "you cannot use a good external model on this code at all". Substituting placeholders converts that into "you can".

Rehydration is handled by narrowing rather than by cleverness: only values that need no JSON escaping are ever spliced back, so a placeholder inside a tool-call argument string is safe. Detection is prefix- and context-driven rather than entropy-scored, because a false positive silently damages a prompt, which is worse than a miss.

Turn it on
[interceptor.redact]
enabled = true
rehydrate = true
extra_literals = ["build01.internal.invalid"]

Settings › Redact and route — including extra_literals as a comma-separated list, for the things detectors cannot know about, such as internal hostnames.

Use it

Nothing to drive. The streaming rehydrator holds back a chunk tail so a placeholder split across two chunks is still matched, and hands the text layer only complete UTF-8.

Caveat

A value that would need JSON escaping — a private-key block — is redacted and stays redacted rather than corrupting a response body. Redaction never suppresses reject_sensitive; if both are on, the strict one still applies.

Memory

17

Cross-agent shared project memory

memory
What it is

A project-scoped store of prior findings, decisions, and dead ends, injected into whichever agent is running. A note written from Codex is read by Claude Code, and the other way round.

Why

Each agent CLI keeps its own history and shares nothing with the others. The proxy sees all of them, so it is the only place this can live.

Two limits are deliberate. The store is written and read by explicit direction only, because nothing else here can be undone: a wrong inference would be silently prepended to every later request in the project. And the injected block is hard-bounded and labelled as prior context rather than as instructions, because it is paid for on every turn and read by a model that will otherwise treat it as a directive.

Turn it on
[memory]
enabled = true
inject = true
max_notes = 64
max_note_chars = 2000
max_injected_chars = 6000

Settings › Shared project memory

Use it

From any agent, at the start of a message:

remember: rayon made the parser slower, do not retry it
recall:
forget:
See it

Routing › Project memory — a project selector, the note list, and a form to record one by hand. Notes live in ~/.llmproxy/memory/<project>.json, owner-only.

Caveat

Memory writes are refused while reject_sensitive is on: a note outlives the request that carried it, so an unscreened one would turn a single exposure into a standing one.

Still open: nothing captures memory automatically. Automatic extraction is the obvious next step and the obvious way to poison the store; it wants an explicit review step before anything reaches injection.

Platform

The parts that make a routing policy something you can change with confidence, and watch while it runs.

18

Routing regression suite

platform
What it is

Real requests captured from the decision audit, replayed against an edited prompt or target set, and diffed.

Why

Single-shot route testing answers "where would this one prompt go". The question that actually matters when you edit a policy is "what did this change move" — and without an answer, a prompt edit is a matter of taste. With one, it is falsifiable in CI.

Use it

In the interface: Routing › Policy & test › Routing regression suite — Capture from decisions, Download corpus, edit your prompt or targets, then Replay & diff.

In CI:

llmproxy --route-corpus corpus.json --route-corpus-mode integrated

It exits non-zero when a decision moved. The same corpus is available at GET /api/route-corpus.

See it

The results table lists only what moved, with the recorded destination beside the new one.

Caveat

Decisions that mean the same destination compare as one — a sticky reuse and a cached replay are both "it went to that target" — and a new case is not a regression.

19

Per-provider flow ribbons

platform
What it is

The Overview flow diagram, with one ribbon per provider actually serving traffic, thickness by volume.

Why

Four decisions are easy to get wrong here, so they are fixed deliberately:

  • Colour stays bound to locality, not provider identity. The whole interface encodes local and external through one mint/amber pair; per-provider hues would break that. Identity is carried by stable position and a direct label, so it is never colour-alone.
  • Ribbon order is stable, never sorted by volume, or providers would swap places on every poll. Group by locality, then sort alphabetically; only thickness varies.
  • The fan-out is capped at about six ribbons, beyond which labels collide; the tail folds into one aggregate.
  • Updates are keyed, not wholesale, because rebuilding the nodes each poll restarts the drift animation and visibly stutters.
See it

Overview › Traffic pulse — ribbons, the local/external split band, p50 and p99 latency bars, and stat tiles for requests, remapped, intercepted, local, external, spend, and tokens.

20

Triage payload trimming

platform
What it is

The copy of the conversation sent to triage keeps every system message plus the newest window of turns, instead of the whole thing.

Why

The whole client conversation used to be copied, so triage input grew with conversation length — you paid more for routing the longer you worked. Trimming also reduces the noise your route hints are matched against.

Turn it on
[interceptor]
triage_max_messages = 24   # 0 copies the whole conversation

Settings › Redact and route › triage_max_messages

Caveat

The window is trimmed from the front until it starts on a user turn, so a tool result never arrives without the assistant call that produced it.

Still open: the window is a message count. Trimming by token budget would track the real cost more closely, at the price of a tokenizer the proxy does not have.

21

Logs, decisions, and diagnostics

platform
What it is

Three layers: a live traffic log and error feed here, a bounded 24-hour decision audit with prompt previews, and a full request/response TRACE file on disk.

Turn it on
max_logging_retention_days = 7   # 0 keeps logs indefinitely

Settings › log retention days. Cleanup runs at startup and removes only matching llmproxy log files.

See it
  • Activity › Decisions — why triage chose what it chose, the requested model, triage model and latency, the finalized provider and model, and any fallback error. Filter by text or outcome, and send any prompt straight into the route tester.
  • Activity › Event log — live traffic and recent errors, both clearable.
  • ~/.llmproxy/llmproxy-yyyymmddhhmmss.log — full bodies. HTTP failures, stream failures, and timeouts are ERROR events.
Caveat

Log files are owner-only (0600 on Unix) and never contain authorization headers. Screened and rejected prompts are redacted in both the trace and the audit.

--upstream <url>override the external base URL; rejected by --proxy and --integrated launchers, which take their destination from config
--codex --claude --copilotlaunch that agent through the proxy
--proxy --intercept --integratedmode override; integrated is the default
--codex-bin <path>agent executable; also --claude-bin, --copilot-bin
--project <dir>use this project's .llmproxy.toml instead of the nearest one
--no-projectignore any project overlay for this launch
--route-corpus <file>replay a corpus, print the diff, exit non-zero when a decision moved
--route-corpus-modeintercept or integrated
--restart / --shutdownreplace or stop the managed daemon
-- <args>everything after the separator is passed to the agent

What disables what

Features that silently switch other features off. If something looks dead, this table is the first place to check.

second_opinion or shadow streaming, for the requests they touch a diff needs both complete answers

no embeddings provider routing cache, drift re-triage, retry escalation all three are embedding distances

Troubleshooting

reference
symptomfirst thing to check
Config edit had no effectThe file is not live on its own — restart, or edit through this interface, which validates and swaps atomically.
Everything goes to one providerThe agent is sending an explicit model rather than Auto, or the mode is --proxy.
Routing ignores a new targetIts hint overlaps a broader route's. Hint wording must stay disjoint — there is no tie-break yet.
A conversation will not change routeIt is pinned. Send unstick:, or set sticky_absolute_ttl_secs / sticky_max_turns: the idle TTL alone bounds nothing during active work.
Spend shows no dollar figureNo [providers.*.pricing] for that provider, or it is marked subscription = true.
Leaderboard is empty or unrankedNo writable ~/.llmproxy, or rows are still below the sample-size floor.
Cache, escalation, or speculation never firesreject_sensitive is on, or no embeddings provider is configured. See What disables what.
Shadow tab stays empty[integrated.shadow] enabled is off, or the sample rate has not come round yet — it is an exact one-in-N counter.
Second opinion never appearsIt is config-file only, and either side asking for a tool call cancels it.
Admin UI shows a "files not found" pageThe ui/ directory is not beside the binary. Set LLMPROXY_UI_DIR or [admin] ui_dir; release builds read it once at startup, so restart after installing.
